Lumen — Solana Arb (private use only)

May 2024 — present · three major versions, the current one is a full rewrite

GitHub repo: PRIVATE FOR A REASON · Program: Solscan — the on-chain half is open for anyone to read


An arbitrage system for Solana DEXes that I have been building since May 2024. It has gone through three architectures: an indexer over a self-hosted Jupiter API, then its own indexer and simulation service, and now Lumen — a shred-driven SVM bank that reacts to transactions before the chain confirms them.

v3 — Lumen (2026, current)

The previous versions waited for state: an indexer told the bot a pool had changed, and only then could it price and act. Lumen removes the wait. It consumes the raw shred stream, simulates every relevant transaction in an embedded solana-svm engine against a speculative copy of chain state, and prices what that transaction did to the pool while the chain is still confirming it.

  • A private bank: LMDB-backed accounts, a real SVM on top, two forks over the confirmed root in the shape of agave's own bank forks — a speculative head the hot path reads, and a pending fork where confirmed blocks are replayed and hash-verified against the network before they are promoted.

  • An account-lock scheduler modeled on agave's AccountLocks / unified scheduler: conflicting transactions simulate strictly in order, independent ones in parallel, O(accounts) per scheduling event.

  • Hand-built thread pipeline, no async runtime on the hot path: router, core-pinned workers, executor gate, dispatcher — each stage with its own histogram.

  • Chain-exact details I got wrong first and fixed by reading the validator: blockhash from the slot's last tick, lookup-table slot rules, program delay visibility.

  • A sender router over Jito, Astralane, Helius, NextBlock, 0slot, Falcon, FlashBlock and direct TPU, probed continuously so each transaction takes the path closest to the current leader.

A real Raydium V4 swap simulates in about 0.2 ms p50 on the production Xeon with the x86-64 JIT. The other rows are the same benchmark on an Apple M-series laptop, where only the sBPF interpreter exists — a pessimistic floor, not the real cost:

PlohoyStream

Jun 2026 — active development

GitHub repo: BadStream


Turns an Android phone into a self-contained live-streaming camera — point it at a scene, pick a destination, go live to any RTMP, RTMPS or SRT ingest. Inspired by Moblin on iOS, aiming for a real broadcast tool rather than a toy.


The transport stack is written from scratch in native C/C++ instead of wrapping a black-box SDK — RTMP handshake, chunking, AMF0 and FLV, MPEG-TS muxing, and SRT through libsrt — so the entire streaming path stays under the app's control.


  • H.264 and H.265 with automatic codec negotiation, HDR (HLG10) capture-to-encode where the device supports it, and graceful SDR fallback.

  • Adaptive bitrate in the native layer, foreground-service streaming that survives backgrounding, and local MP4 recording alongside the live feed.

  • Dual-camera picture-in-picture: two independent Camera2 inputs composited through a shared GLES compositor. The PiP window is draggable, resizable and corner-snapping, and tap-to-swap between cameras is blink-free because both run as separate inputs.

  • Capability-driven — reads each device's certified concurrent-camera combinations at runtime and only offers lens and PiP pairs the hardware actually supports, degrading instead of failing.

  • OBS WebSocket remote: list and switch scenes and start or stop the OBS stream from the phone, with automatic "Be Right Back" switching when link health degrades.


Kotlin and Jetpack Compose (Material 3) on top of the native core over JNI, with a landscape-first viewfinder.
